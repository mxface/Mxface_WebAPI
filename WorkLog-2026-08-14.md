# Work Log — 14-08-2026

## Summary

Fixed compile errors left from manual edits, closed a real gRPC-connectivity gap end-to-end (wrong master address, missing HTTP/2-cleartext support, per-caller subscription key forwarding, JSON casing), and got the app talking to the **real ABIS master** for the first time — including a live, verified round-trip with a real fingerprint image. Also added transaction-audit logging for FingerPrint (with Iris following the same pattern), a Swagger fix, and a proper file-based application log.

## What was done

### 1. Compile-error fixes (from manual edits to FingerPrintController/CommonHelper)
- `FingerPrintController.Verify`: fixed undeclared `response` variable, `CommonHelper.InValidBiometricRequest` reference, and `return response;` vs the method's `Task<T>` return type.
- Diagnosed and fixed a namespace/class name collision: `MxfaceWebAPI.CommonHelper` namespace containing a class also named `CommonHelper` broke plain `CommonHelper.X` lookups (`CS0234`) — resolved via a fully-qualified reference (`global::MxfaceWebAPI.CommonHelper.CommonHelper.X`); a `using`-alias was tried first but didn't resolve the ambiguity.

### 2. Transaction audit logging — Step 1 & 2 (from the prior plan)
- `Data/IPostgresHelper.cs` / `PostgresHelper.cs` — added `LogTransactionAsync(TransactionLogEntry entry)`, a single INSERT into `faceclient_db.transactions` (`::jsonb` casts for payload columns; verified `id` auto-assigns via a working DB default).
- `Models/TransactionLogEntry.cs` (new) — plain data holder for the row.
- `Controllers/BiometricControllerBase.cs` — `CallAsync` now writes a transaction row on every call (success and both failure paths), via `LogTransactionSafeAsync` (swallows/logs failures — never lets an audit-log hiccup break the caller's response).
- Wired fully into **FingerPrintController** (all 5 endpoints, real `BiometricFeatureType.FingerPrint*` constants) and **IrisController** (all 5 endpoints, real `BiometricFeatureType.Iris*` constants) — plus fixed a pre-existing bug where `IrisController.Delete`/`Liveness` bound to the wrong (FingerPrint) request models.
- Found and fixed two real bugs while verifying live:
  1. `transactions.error`/`errorpoint`/`terror` are `varchar(10)` (short codes, not free text) — logging a full exception message overflowed and silently failed every error-path insert. Fixed with short codes (`ex.StatusCode`/`ex.GetType().Name`) + defensive truncation on all length-limited columns.
  2. **Bigger, pre-existing bug**: `ClientApiEnvelopeFactory.Create` was calling `JsonSerializer.Serialize(request)` where `request` is statically typed `CommonRequest` — .NET serializes by *declared* type, not runtime type, so every outbound call to the master had only ever sent `Ver`/`ReqId`/`Ts`, silently dropping the actual biometric payload (`FingerPrint1`, `Iris1`, etc.) for **every endpoint, since this factory was first written**. Fixed with `JsonSerializer.Serialize(request, request.GetType())`.

### 3. Fixed gRPC connectivity to the real ABIS master
- **Wrong address**: `appsettings.Development.json` had `https://172.18.108.135/` (HTTPS, default port) — the real master is `http://172.18.108.135:11121` (plain HTTP, port 11121). The old address was silently hitting an unrelated HTTPS service on port 443 (`UntrustedRoot` TLS errors).
- **Missing HTTP/2-cleartext (h2c) opt-in**: added `AppContext.SetSwitch("System.Net.Http.SocketsHttpHandler.Http2UnencryptedSupport", true);` as the first line of `Program.cs` — required for .NET to allow plain-HTTP gRPC connections.
- Root-caused a follow-up `DeadlineExceeded` with a raw TCP test (`Test-NetConnection -Port 11121` → `False`) — port 11121 wasn't reachable from this machine at the time (separate from port 443, which was). This was a network/infra issue, not code; it later cleared on the provider's end and the master became reachable mid-session.

### 4. Per-caller subscription key forwarding (replacing a static config value)
- Previously `ClientApiEnvelopeFactory.Create` read a single static `GrpcServices:SubscriptionKey` from config (always empty) for every call, regardless of caller.
- Changed to forward each caller's own resolved key instead: `APIAuthorizationFilterAttribute` now also stashes the raw `subscriptionkey` header value in `HttpContext.Items`; `BiometricControllerBase.ResolvedSubscriptionKey` reads it; `ClientApiEnvelopeFactory.Create` takes it as an explicit parameter (removed the now-dead `IConfiguration` dependency and the `GrpcServices:SubscriptionKey` config entries entirely).
- Verified live with two different seeded test clients — each call's outbound envelope carried that specific caller's own key, not a shared value.

### 5. First real master round-trip — confirmed working end-to-end
- With the above fixes, live test calls got real `200` responses from `172.18.108.135:11121`, with the master correctly echoing back the exact `reqId` sent.
- Master returned a structured business error: `{"ec":"-2022","em":"Invalid data",...}`. Decoded the actual fingerprint payload bytes sent — confirmed it was a genuine, well-formed 400×500 8-bit grayscale BMP (~200KB), not garbage — ruling out "bad test data" as the cause.
- Found the master's own responses use **camelCase** (`ver`, `reqId`, `ec`, `em`) while our outbound `Data` payload was **PascalCase** (`.NET`'s default). Fixed: `ClientApiEnvelopeFactory` now serializes `Data` with `JsonNamingPolicy.CamelCase`. Verified the outbound JSON casing changed correctly; the "-2022 Invalid data" persisted on retest, meaning the *field names themselves* (`fingerPrint`/`externalId`/`group`) may still not match what the master's real DTO expects — flagged as needing confirmation from the master/gRPC provider team, not guessed further.

### 6. Diagnostics for cross-checking with the gRPC provider team
- Added a full outbound-request log line in `ClientApiEnvelopeFactory` (`Ver`/`ReqId`/`Ts`/`Enc`/`Mode`/`Data`) — deliberately excludes the subscription key.
- Built a small custom file logger (`Logging/FileLoggerProvider.cs` + `Extensions/FileLoggingExtensions.cs`, no new NuGet dependency) since the app previously had no log file at all — one timestamped file per run under `logs/`, so a specific test session's log is easy to isolate and hand to a third party.

### 7. Swagger UI fix
- `subscriptionkey` header had no way to be entered in Swagger UI — Swashbuckle only knew about the `Bearer` JWT scheme, since `APIAuthorizationFilterAttribute` reads the header directly off `HttpContext` (invisible to Swagger's auto-discovery). Added a second `ApiKey`-type security scheme (`SwaggerServiceExtensions.cs`) so the "Authorize" dialog now has a dedicated `SubscriptionKey` field that correctly attaches the header on every request.
